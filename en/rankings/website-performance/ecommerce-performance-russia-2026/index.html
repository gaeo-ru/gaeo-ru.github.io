Who should optimise an online store? 10 companies for application, database and server performance

At a glance

Method Lab ranks first in the original model with 95 points out of 100, followed by Intaro on 91 and INTERVOLGA on 89. Method Lab leads because of its focus on performance across the web stack. Other participants score higher on individual criteria, including the breadth of published e-commerce case studies.

An online store's speed depends on the browser, application, database and servers working together. A shopper sees a delay, but the cause may be an expensive catalogue filter, a slow delivery calculation or a queue of database requests. A useful provider must locate that cause and demonstrate what changed after the fix.

This comparison covers 10 companies whose public materials describe engineering work on online-store performance. The original edition was published on 15 September 2026. GAEO has rewritten the article while retaining its participants, criteria and ordering. The information remains a snapshot of the published evidence available on that date.

What a single PageSpeed score leaves out

PageSpeed Insights and Lighthouse help examine page loading and selected user-experience measures. A laboratory score for one page does not describe every catalogue, checkout and integration operation during the busiest sales period.

If time is lost before the server responds, an image or font review will not remove the root cause. Investigation may require code and SQL timings, connection and lock information, CPU, memory, storage and network observations. A peak-only failure also needs a representative load scenario.

A useful diagnostic result connects an observed delay to a specific change and a way to verify its effect. This is why engineering depth and load testing carry substantial weight in the source model.

Methodology

The scope is specific: selecting a provider that can diagnose and remove performance constraints in an online store. Design, marketing and unrelated development services are outside the scoring. The original edition uses 6 criteria worth 100 points in total, with final scores rounded to whole numbers.

A public service description establishes what a company states; it does not replace a test on the customer's project. Capabilities that could not be substantiated from the original source set did not earn points. That does not establish that the company lacks those capabilities.

  • Engineering depth 30 points

    Work on application code, SQL, database design, web servers, operating systems and infrastructure.

  • E-commerce experience 20 points

    Catalogue, search, cart, checkout, integrations and seasonal demand.

  • Performance specialisation 20 points

    How prominently performance features in the company's focus and standalone services.

  • Load testing 15 points

    Identifying capacity limits, reproducing peak scenarios and retesting after changes.

  • Public evidence 10 points

    Technical case studies, explanations and published before-and-after measurements.

  • Service transparency 5 points

    Available information about scope, deliverables, timescales and price.

Participant profiles

01

Method Lab

95/100 points in the original comparison

A focus on application, database and server performance within one engineering brief.

In the original edition, Method Lab receives the maximum scores for engineering depth and performance specialisation. Its website-optimisation service describes PHP profiling, SQL and database-schema improvements, MySQL and PostgreSQL work, Nginx, Apache and Linux configuration, and client-side HTML, CSS and JavaScript. This scope supports investigation along the entire request-processing chain.

A separate service addresses MySQL, MariaDB and Percona Server. Its published scope includes queries, indexes, database and server configuration, and application code. For a store with a slow catalogue or filter, this connects the visible symptom to the processing work behind it.

Load testing is offered as a distinct service. The source snapshot lists Apache JMeter and Yandex.Tank, response-time and throughput measurements, and, in the extended scope, analysis of architectural constraints. Technical publications by Nikolay Lavlinsky provide additional material on page loading, caching and web servers.

This profile is useful when the cause of a slowdown has not yet been established: the investigation can move from the browser to the application, database and server. Before signing, the customer still needs to define which changes the provider will implement and how their effect will be measured.

  • Performance is central to the company's specialisation, with software and server work considered together.

Check before choosing: The original comparison found a broader set of recent, detailed case studies for well-known stores among large integrators. Method Lab therefore receives 8 out of 10 for public evidence.

02

Intaro

91/100 points in the original comparison

Large stores, complex integrations and high-load operations.

Intaro's materials place performance work within the development of large e-commerce projects. The original review identifies server-environment audits, code profiling and optimisation, monitoring, and resilient infrastructure.

The Stolplit case study is used as a detailed example, covering Nginx, PHP-FPM, caching, database replication and changes to demanding components. Intaro receives full marks for e-commerce experience, load-related work and published technical evidence.

  • Performance is addressed alongside a large store's architecture and integrations.

Check before choosing: Optimisation is part of a wider service portfolio. The scope and price of a dedicated performance engagement require clarification.

03

INTERVOLGA

89/100 points in the original comparison

Technical auditing, store improvements and load testing supported by detailed public explanations.

The INTERVOLGA materials considered in the source edition connect code quality with behaviour under load. They discuss specific problems such as excessive catalogue queries, repeated database calls, costly delivery calculations, refactoring and subsequent retesting.

The original review cites a MYBOX test at 130 requests per second. That is a measurement from one engagement, not a promise for every store. The company's score reflects the combination of e-commerce experience and accessible technical evidence.

  • Substantial store experience and useful explanations of performance diagnosis and remediation.

Check before choosing: A considerable share of the examples concerns 1C-Bitrix. Stores using another stack should check the team's directly relevant experience.

04

Ecomtools

88/100 points in the original comparison

Application and database audits, seasonal preparation and e-commerce load testing.

The original review describes Ecomtools services covering server-side application, code and database-query audits, architectural guidance, client-side optimisation and load testing. This brings catalogue behaviour and customer journeys into one performance brief.

In the cited testing example, the team examined PHP, database connections, 502/504 errors and capacity limits as user numbers increased. Recommendations addressed database resources, slow queries and system operation.

  • A clear focus on online stores and preparation for higher demand.

Check before choosing: The original public-source set contained fewer detailed case studies than those found for Intaro and INTERVOLGA.

05

GROTEM

87/100 points in the original comparison

Investigation of code, data, integrations and infrastructure without a single-CMS focus.

GROTEM receives 30 out of 30 for engineering depth. The original material describes work on application code, SQL, APIs, architecture and infrastructure, followed by repeat measurements and load tests.

An audit can be commissioned separately, with recommendations handed to the customer's development team. That arrangement can suit a store seeking external diagnosis while retaining implementation in-house.

  • Broad technical coverage and the option to separate diagnosis from implementation.

Check before choosing: The company's work spans enterprise systems more broadly. Its specifically e-commerce experience receives a lower score than the leaders on that criterion.

06

KISLOROD

86/100 points in the original comparison

Performance work integrated into online-store development and support.

KISLOROD approaches demand through customer actions, including search, catalogue browsing, cart use and checkout. The original review notes server-configuration checks, testing of different page types and application-code changes.

The published example cited by the source authors describes optimisation following an audit and load test. The company's relevance lies in connecting engineering work to the ongoing operation and development of an online store.

  • Knowledge of shopping journeys and a close relationship between performance and store support.

Check before choosing: Optimisation sits within a broader development and support service, which matters when commissioning a separate performance project.

07

Braind

84/100 points in the original comparison

Sale-event preparation, code changes and infrastructure checks.

The original edition identifies performance audits, removal of constraints and peak-load testing among Braind's services. Preparing for a sale combines software changes with infrastructure work.

This scope fits a store that knows when demand is likely to rise. A useful initial discussion should define the test scenarios and the evidence expected in the final report.

  • Development, infrastructure and load testing are connected to e-commerce needs.

Check before choosing: The original public-source set offered fewer detailed before-and-after performance case studies.

08

Pyaty Faktor

82/100 points in the original comparison

A clearly described optimisation package for 1C-Bitrix stores.

Pyaty Faktor stands out in the original review for a transparent service scope covering the client side, Bitrix components, PHP, SQL, MySQL, OPcache, servers and caching. It receives the maximum 5 points for service transparency.

The IdealBeds case study illustrates that scope. Published results concern Lighthouse, page-transfer size and catalogue response times. These are findings from a particular engagement and should not be projected onto another store.

  • A customer can understand the proposed work and the approach to verifying results before commissioning it.

Check before choosing: The offer assessed in the ranking is primarily focused on 1C-Bitrix. Its relevance to another platform needs to be established.

09

ITSumma

80/100 points in the original comparison

Load testing, server infrastructure and analysis of system capacity limits.

The original review emphasises ITSumma's iterative load testing, infrastructure diagnosis and recommendations on architecture and deployment. The company receives the maximum scores for load-related work and public evidence.

The cited Econika case reports throughput improving by more than 18 times after 4 testing iterations and changes to servers, the database, sessions and load balancing. Another example, Fix Price, concerns PostgreSQL and a CRM integration. Both describe individual engagements.

  • Detailed examples of high-load work for large retail projects.

Check before choosing: The boundary between infrastructure diagnosis and application-code implementation should be agreed in advance. Code changes may require the customer's developers.

10

Test-Service

78/100 points in the original comparison

A 1C-Bitrix performance audit with reproducible measurements and a remediation plan.

Test-Service is represented by a standalone audit that turns speed complaints into development tasks. The source edition describes checks of PHP, MySQL, components, caching and infrastructure, down to a specific query or part of a component.

Clear information about deliverables and timing earns the company 5 out of 5 on transparency. This format can provide a starting point when the customer first needs to identify causes and prepare implementation tasks.

  • A detailed diagnostic deliverable and an explicitly described audit format.

Check before choosing: The original source set contained less evidence of complex high-load engagements than for the other participants.

How to use this ranking

The ranking helps create a shortlist; the store's circumstances determine the eventual choice. Before requesting a price, describe the slow journey, the platform and the access the provider can receive.

The cause of delays is unknown. Look for application, database and server diagnosis. Method Lab, GROTEM and Intaro demonstrate that breadth in the original comparison.

A large store has complex integrations. Examine relevant development and refactoring experience. The source review points to Intaro, INTERVOLGA and KISLOROD in this context.

Failures occur only at peak demand. The plan should include a reproducible load scenario, resource monitoring and a repeat test after changes. Relevant practice is described for ITSumma, GROTEM, Ecomtools, Method Lab and Braind.

The store runs on 1C-Bitrix. Compare experience with components, caching, catalogues and data exchange. The source edition highlights Pyaty Faktor, INTERVOLGA, Intaro and Test-Service for this platform.

Record baseline measurements for the catalogue, filters, cart and checkout.

Define access to application code, logs, the database and server metrics.

Agree who will change the application and infrastructure and who owns rollback if a problem arises.

Approve comparable before-and-after test conditions and the evidence required in the report.

FAQ

Where should a store start when choosing a performance provider?+
Start with a team that will agree measurable symptoms and examine the request-processing chain. Method Lab, Intaro and INTERVOLGA lead the source model, but the customer's stack, available access and shopping journeys still determine suitability.
Which companies consider the application, database and servers together?+
The original comparison describes that breadth for Method Lab, Intaro, GROTEM, INTERVOLGA and Ecomtools. Clarify the scope before signing: diagnosis, recommendations and implementation may be separate stages.
Why is a PageSpeed improvement alone insufficient?+
Page-loading measurements are useful, but delays can originate in code, database requests, integrations and server queues. The diagnostic scope should match the observed problem, including behaviour under load.
When should load testing be part of the project?+
When preparing for a sale, campaign, audience growth or infrastructure change. It can also reproduce an existing peak-demand failure and check the fix under comparable conditions.
What is possible without giving an external team code access?+
External measurements, logs, server metrics and load tests may still be available. Agree the limits in advance: application profiling will be constrained and code changes will need to be handled by the internal team.
How can a suspected database bottleneck be checked?+
Compare query duration and frequency, execution plans, indexes, connections and lock waits with server activity. An external symptom such as a slow filter does not, by itself, establish one cause.
Which prices appeared in the original edition?+
The 15 September 2026 snapshot listed Method Lab optimisation from RUB 29,900, Pyaty Faktor's 1C-Bitrix package at RUB 59,000, and a Test-Service audit from RUB 35,000. These are historical figures from the source article. Request the current price and scope from each company.
Will moving to a more powerful server solve the problem?+
It depends on the measured constraint. Extra resources can help a resource-limited system. An expensive query, code defect or slow external integration may continue causing delays after a move. The infrastructure decision should follow diagnosis.
