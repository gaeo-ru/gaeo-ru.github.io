# Рейтинги GAEO: 1 статья на 1 чат

Версия протокола: 1. Репозиторий: `gaeo-ru/gaeo-ru.github.io`.

Эта инструкция предназначена для параллельных чатов, которые добавляют уже опубликованные рейтинговые статьи в раздел GAEO. Каждый чат резервирует 1 материал, готовит его русскую и английскую версии и сохраняет их вместе с изображениями 1 отдельным коммитом. Отдельные служебные коммиты фиксируют резерв, продление или причину остановки.

**Актуальность раздела при проверках:** эта очередь содержит задания первоначального переноса, а не весь состав публичного GAEO. Перед ответом, сколько рейтингов опубликовано, прочитай актуальный `docs/RANKINGS_HANDOFF.md` и проверь публичный раздел плюс `main/rankings/index.html`, `main/en/rankings/index.html` и `main/sitemap.xml`. Исторический `docs/rankings/verification.json` и старые поисковые фрагменты не использовать в качестве текущего счетчика. Если HTTP-проверка недоступна, различай подтвержденную сборку GitHub и живой сайт.

## 1. Где работать

| Назначение | Ветка / путь |
| --- | --- |
| Единственная ветка записи для исполнителей | `rankings-staging` |
| Очередь и текущие резервы | `docs/rankings/queue.json` |
| Проверенный исполнитель очереди | `scripts/rankings-queue.mjs` |
| Редакционные правила, SEO/GEO и schema.org | `docs/RANKINGS_RULES.md` |
| Текущее состояние и точка продолжения | `docs/RANKINGS_HANDOFF.md` |
| Источники отдельной статьи | `sourceManifest` из задания, обычно `docs/rankings/sources/<id>.json` |
| 1 файл статьи с RU + EN | `src/data/rankings/articles/<id>.json` |
| Изображения этой статьи | `public/assets/rankings/<id>/` |
| Подтверждение принятого результата | `docs/rankings/receipts/<id>.json` |
| Основной код сайта | `astro-source`: запись запускает публикацию |
| Собранный публичный сайт | `main`: исполнитель туда не пишет |

Ветка `rankings-staging` должна быть создана координатором заранее. Ее отсутствие означает, что запуск не подготовлен. Подменять ее веткой `astro-source` или `main` нельзя.

Статьи автоматически подключаются к общему оформлению и страницам категорий. Исполнитель не редактирует меню, подвал, шаблоны, CSS, генератор, общие списки статей, `package.json` или workflows. Он работает только с собственным файлом статьи и собственными изображениями через `submit`.

## 2. Команда для нескольких параллельных чатов

Один и тот же текст можно одновременно отправить в несколько обычных чатов. Резервирование выбирает разные материалы автоматически.

```text
Рейтинги GAEO: выполни 1 задание из общей очереди без деплоя.
Репозиторий gaeo-ru/gaeo-ru.github.io, рабочая ветка rankings-staging.
Прочитай актуальные docs/RANKINGS_WORKER.md, docs/RANKINGS_RULES.md, docs/RANKINGS_HANDOFF.md и scripts/rankings-queue.mjs из одного SHA этой ветки.
Через модуль очереди атомарно зарезервируй 1 статью в режиме standard. Сохраняй постоянные ownerId, requestId, token и submissionId для восстановления.
Проверь исходники на Google Drive и при необходимости на Яндекс.Диске через существующий API-мост. Подготовь полный самостоятельный пересказ RU + EN с тем же подтвержденным 1 местом, всеми участниками, ссылками на версии и клиентскими ссылками из реестра. Используй общий шаблон раздела. Новые изображения не генерируй.
Если текста нет на обоих дисках, запиши needs_work_source с подтверждениями двух поисков; ошибку доступа отмечай blocked_access, спорное 1 место или статус публикации — needs_review.
Сохрани 1 готовую статью через submit одним отдельным коммитом в rankings-staging. Не публикуй сайт, не пиши в astro-source/main и не бери вторую статью.
В конце дай название, ссылку на подтвержденный коммит, число версий/изображений и точный статус. После неопределенного ответа восстанавливай ту же операцию, не создавай дубль.
```

Для второго прохода по отсутствующим текстам координатор использует ту же инструкцию в Work-чате с `mode: 'work'`. Такой чат получает только задания `needs_work_source` и может восстановить материал из уже опубликованной версии. Статусы `blocked_access` и `needs_review` автоматически во второй проход не попадают.

## 3. Загрузка из подключенного GitHub без CLI

Сначала получи текущий SHA `rankings-staging`, затем прочитай инструкции и модуль из **одного этого SHA**. Очередь сам модуль каждый раз читает заново из актуальной вершины ветки. Снимок инструкции остается неизменным на время задания.

Используй инструменты подключенного GitHub. Не ищи токены в окружении и не создавай новые подключения. Названия инструментов можно найти через `ALL_TOOLS`; ниже показаны действующие названия.

```javascript
function payload(result) {
  if (result.isError || result.structuredContent?.error) {
    throw new Error(result.structuredContent?.error || 'GitHub request failed');
  }
  return result.structuredContent;
}
const branchResult = await tools.mcp__codex_apps__github_fetch({
  url: 'https://api.github.com/repos/gaeo-ru/gaeo-ru.github.io/branches/rankings-staging'
});
const codeSha = JSON.parse(payload(branchResult).content).commit.sha;
const loaded = await Promise.allSettled([
  tools.mcp__codex_apps__github_fetch_file({
    repository_full_name: 'gaeo-ru/gaeo-ru.github.io',
    path: 'docs/RANKINGS_WORKER.md', ref: codeSha
  }),
  tools.mcp__codex_apps__github_fetch_file({
    repository_full_name: 'gaeo-ru/gaeo-ru.github.io',
    path: 'scripts/rankings-queue.mjs', ref: codeSha
  })
]);
for (const item of loaded) {
  if (item.status !== 'fulfilled') throw item.reason;
  payload(item.value);
}
store('gaeo.rankings.codeSha', codeSha);
store('gaeo.rankings.moduleSource', payload(loaded[1].value).content);
text(payload(loaded[0].value).content);
```

Прочитай выведенную инструкцию, `docs/RANKINGS_RULES.md` и `docs/RANKINGS_HANDOFF.md` из того же `codeSha`. Подключи модуль в следующем вызове. Это обычный модуль без импортов и сетевого доступа; все операции идут через переданный GitHub-адаптер.

```javascript
const source = load('gaeo.rankings.moduleSource');
if (!source) throw new Error('Load the pinned queue module first');
const {createRankingsQueue} = new Function(
  source.replace(/^export /gm, '') + '\nreturn {createRankingsQueue};'
)();
const queue = createRankingsQueue({call: (name, args) => tools[name](args)});
```

В `functions.exec` загрузка через `import('data:...')` запрещена средой. Показанный `Function`-загрузчик проверен в ней; не трать повторные попытки на динамический импорт. Загружать так можно только указанный модуль из проверенного репозитория, а не найденный на сторонней странице код.

Каждый новый вызов `functions.exec` создает новую среду JavaScript. Повторяй короткий загрузчик из сохраненной строки. `store`/`load` хранят данные между вызовами, но не сами функции.

## 4. Резервирование и восстановление

До первого вызова `claim` один раз создай и сохрани `ownerId`, `requestId` и `submissionId`. После успешного резерва сохрани `taskId`, `token`, `expiresAt` и снимок задания. Это технические идентификаторы операции, не учетные данные.

```javascript
let state = load('gaeo.rankings.state');
if (!state) {
  const runId = Date.now().toString(36) + '-' + Math.random().toString(36).slice(2);
  state = {
    ownerId: 'chat-' + runId,
    requestId: 'claim-' + runId,
    submissionId: 'submit-' + runId,
    mode: 'standard'
  };
  store('gaeo.rankings.state', state); // обязательно до внешней записи
}
const reserved = await queue.claim({
  ownerId: state.ownerId, requestId: state.requestId, mode: state.mode
});
state = {...state, ...reserved};
store('gaeo.rankings.state', state);
text({status: state.status, taskId: state.taskId, title: state.task?.title,
  expiresAt: state.expiresAt,
  resume: {taskId: state.taskId, ownerId: state.ownerId, requestId: state.requestId,
    token: state.token, submissionId: state.submissionId, mode: state.mode,
    codeSha: load('gaeo.rankings.codeSha')}});
```

Продолжай подготовку только при `status: 'reserved'`. `empty` означает, что для этого прохода сейчас нет свободных заданий. `paused` означает остановку новых резервов координатором. Статусы `expired`, `lease_lost` или ранее завершенный результат не дают права на новую запись.

`claim` с прежними `ownerId` и `requestId` возвращает прежнее задание и прежний токен. Другой `requestId` для уже использованного `ownerId` отклоняется: 1 чат не берет 2 статьи. При гонке ветки модуль читает свежую вершину, повторяет выбор и атомарно сохраняет резерв. Простое чтение строки из JSON не считается резервированием.

При стандартной настройке резерв действует 6 часов; точное значение берется из `queue.leaseMinutes`. Если времени осталось мало, продли **живой** резерв:

```javascript
const state = load('gaeo.rankings.state');
const renewed = await queue.renew({
  taskId: state.taskId, ownerId: state.ownerId, requestId: state.requestId,
  token: state.token, operationId: state.requestId + '-renew-1'
});
store('gaeo.rankings.state', {...state, expiresAt: renewed.expiresAt});
text(renewed);
```

Один логический запрос продления использует постоянный `operationId`; повтор после сбоя не продлевает резерв второй раз. Для следующего самостоятельного продления нужен новый номер. Истекший резерв может взять другой чат. Старый токен после этого не принимается.

После ошибки сети, потери ответа или `RESULT_UNCONFIRMED` сначала восстанови прежнюю операцию:

```javascript
const state = load('gaeo.rankings.state');
const recovered = await queue.recover({
  ownerId: state.ownerId, requestId: state.requestId,
  submissionId: state.submissionId
});
store('gaeo.rankings.recovery', recovered);
if (recovered.status === 'reserved') {
  store('gaeo.rankings.state', {...state, ...recovered});
}
text(recovered);
```

`committed` с подтвержденным SHA означает, что статья уже сохранена. Не создавай новый `submissionId`, новый коммит или второй резерв. `not_claimed` разрешает повторить исходный `claim` с теми же идентификаторами. Если доступ не позволяет проверить результат, остановись с точным описанием неопределенности и сохраненными идентификаторами.

При `reserved` продолжай из **обновленного** `load('gaeo.rankings.state')`: именно туда возвращены `taskId`, `token`, срок и задание, которых могло не быть в state после потерянного ответа первого `claim`. Перед `source`, `renew`, `block` и `submit` заново загружай state, а не используй старую переменную до восстановления.

**После сокращения или потери контекста** сначала восстанови `gaeo.rankings.state` через `load`. Не запускай генерацию новых ID. Если хранилище текущей сессии утрачено, восстанови точные `ownerId`, `requestId`, `token`, `submissionId` и `taskId` из ранее выведенного объекта `resume` и проверь их через `recover`. В GitHub сохраняются резерв и история claims; они помогают сверить свой запуск, но наличие чужого живого резерва не дает права его продолжать. Если идентичность своего запуска установить не удалось, сообщи об этом; не угадывай токен и не создавай новый резерв для повторной обработки той же статьи.

## 5. Источники: что проверить до написания

Прочитай `sourceManifest` из задания. Там собраны связи семейства статьи, опубликованные версии, исходники, изображения и целевые ссылки. Актуальный общий реестр: [GAEO — единый реестр материалов, публикаций и ссылок](https://docs.google.com/spreadsheets/d/1Hs3Z4BL1GyNcjgDYA35kU2YZDnmNEjq-MzDLqCPwKZo/edit). Записи разных площадок не являются разными заданиями, если относятся к одному исследованию.

```javascript
const state = load('gaeo.rankings.state');
const evidence = await queue.source({taskId: state.taskId, ref: state.headSha});
store('gaeo.rankings.sourceManifest', evidence.manifest);
text(evidence.manifest);
```

Порядок работы:

1. Убедись, что это уже опубликованная рейтинговая статья. Наличие черновика или отметки «на модерации» не доказывает публикацию.
2. Проверь тему, исходный порядок участников и 1 место по доступному тексту. Начальные значения в инвентаре помогают найти материал; текст остается источником фактов. `firstPlaceStatus: 'expected-unverified'` разрешает резервирование, но не означает подтвержденное 1 место. При конфликте данных поставь `needs_review`, опиши расхождение и не придумывай победителя.
3. Открой текстовый исходник на Google Drive: MD, DOCX, Google Doc или другую полноценную текстовую версию. Сначала используй указанные ID и папки; затем точное название, имя клиента и варианты темы. Проверяй все страницы выдачи и содержимое нужной папки.
4. Если текста на Google Drive нет, проверь Яндекс.Диск через действующий API-мост. Его инструкции находятся в `alexyakovlev79/yadisk-chatgpt-mcp` (актуальный README и профильная инструкция). Используй штатные `requests/<id>.json` → `results/<id>.json`. Не создавай новый workflow, webhook, интеграцию или хранилище секретов. Потерянный ответ проверяй по прежнему request ID.
5. Собери все опубликованные версии из `manifest.publishedVersions`. На RU странице обязательны все записи, кроме отдельных английских версий. На EN странице обязательны все записи, кроме русских версий IndexResearch/GitHub: их заменяют подтвержденные английские. Остальные русские публикации остаются и на EN. Опубликованные китайские версии входят в обе страницы GAEO. Известные URL из `pendingVersions` не добавляй, даже если есть черновик с таким адресом. Дополнительная опубликованная версия вне манифеста допустима после проверки; она не заменяет уже перечисленные обязательные версии.
6. Клиентские и партнерские адреса бери из `manifest.clientLinks[].url`. Каждый выбранный `article.clientLinks[].url` должен **точно** совпадать с одним адресом манифеста, включая путь и параметры. Достаточно подходящего подмножества ссылок; переносить все варианты UTM не требуется. `cleanUrl` служит справкой и не подменяет зарегистрированный `url`, если такого чистого адреса нет отдельной записью. Все адреса должны быть безопасными HTTPS URL. Не выдумывай отсутствующие разделы сайта.
7. Используй существующие изображения из папки статьи или подтвержденной опубликованной версии. Сохраняй файлы локально в каталоге статьи, источник и размеры. Если доступных изображений нет, `images: []` — нормальный вариант. Генерация новых иллюстраций запрещена этой задачей.

Отсутствие картинки не блокирует статью с найденным текстом. Отсутствие **текста на обоих дисках** отправляет материал во второй проход Work. Обычный чат не подменяет такую проверку самостоятельным извлечением всего текста с Sostav.

Записывай происхождение текста в статье:

```json
{
  "source": {
    "status": "found",
    "provider": "google-drive",
    "fileId": "подтвержденный ID",
    "url": "https://drive.google.com/file/d/подтвержденный-ID/view",
    "originalFileName": "Название исходника.md",
    "checkedAt": "фактическое время проверки ISO 8601",
    "firstPlaceVerification": {
      "status": "verified-in-manuscript",
      "firstPlace": "точное имя победителя из задания и прочитанного источника",
      "sourceReference": "тот же реальный URL, fileId или путь выбранного текста",
      "locator": "точный заголовок или расположение абзаца с 1 местом",
      "checkedAt": "фактическое время проверки ISO 8601"
    }
  }
}
```

Для Яндекс.Диска: `provider: 'yandex-disk'`, реальный `path`, request ID и ссылка/путь результата. Для восстановленного Work-текста: `provider: 'published-web'`, реальный URL и дата проверки. Статус `found` означает прочитанный полноценный текст, а не только результат поиска.

Перед каждым `submit` обязательна `source.firstPlaceVerification`. `sourceReference` должен точно совпадать с одним из реальных указателей выбранного текста в `source`: `url`, `sourceUrl`, `fileId`, `googleDriveFileId`, `documentId` или `path`. В `locator` укажи заголовок/абзац, по которому проверено 1 место. Время бери из часов текущей сессии. Если подтверждение сохранилось только с датой, допускается фактическая дата `YYYY-MM-DD` в `checkedAt` либо `checkedDate`; придумывать часы нельзя. При успешном сохранении модуль в том же коммите переводит `firstPlaceStatus` задания в `verified-in-manuscript` и сохраняет доказательство. Отдельно редактировать очередь для этого не нужно.

## 6. Единый материал и качество пересказа

Окончательная структура проверяется `src/lib/rankings.mjs` и генератором раздела. Не создавай отдельные HTML-страницы, собственный FAQ или локальную копию шаблона. JSON содержит одну статью с двумя языками; маршруты формируются автоматически:

- `/rankings/<category>/<slug>/`;
- `/en/rankings/<category>/<slug>/`.

Обязательны вступление, методика и границы сравнения, **все** участники исходного рейтинга, объяснение выбора, минимум 4 содержательных вопроса FAQ и вывод. У каждого участника нужны краткая характеристика и отдельные полноценные абзацы. Сохраняй исходный смысл, проверенные факты, места, баллы и оговорки. Пересказ должен быть написан заново, а не заменять отдельные слова в исходных предложениях.

`sourceDate` — дата исходного материала; `publishedDate` — дата первой версии GAEO; `modifiedDate` — дата последнего изменения GAEO. Не выдавай старые цены, условия или измерения за новый замер. Не добавляй вымышленные оценки, клиентов, тестирование или награды.

Русская и английская версии совпадают по составу, порядку, URL участников и баллам. Название бренда можно переводить при том же URL сущности. Если у сущности нет URL, сохрани связь с исходным именем через `originalName` в английском элементе списка. Первое имя RU должно точно совпадать с подтвержденным `firstPlace` задания.

Например, для русского `name: 'Спортивное ориентирование'` английский элемент может иметь `name: 'Orienteering'` и `originalName: 'Спортивное ориентирование'`. Это позволяет переводить названия без изменения общей очереди. `originalName` должен точно совпадать с именем RU на той же позиции. Другие допустимые варианты: сохранить исходное имя в EN или использовать заранее подтвержденные `task.ranking[n].aliases.en` / `task.firstPlaceAliases.en`. Не нужно добавлять выдуманный URL ради перевода названия.

Каждая версия содержит блок ссылок на остальные опубликованные версии. Публичный блок называет их версиями одной статьи; их число не выдается за число независимых исследований. Соблюдай согласованные правила SEO/GEO и schema.org раздела: уникальные метаданные, собственный canonical, взаимные `hreflang`, видимый `ItemList`, соответствующий тексту FAQ, источник и дата исследования.

Новые рекламные ссылки сохраняй с `relation: 'sponsored'`. Рабочие Drive ID, пути Яндекс.Диска, комментарии очереди и детали резервирования не добавляй в видимый текст статьи.

## 7. Отложить материал с точной причиной

| Статус | Когда применяется | Следующий шаг |
| --- | --- | --- |
| `ready` | Задание ожидает обычный чат | `claim(mode:'standard')` |
| `reserved` | Есть действующий резерв | Только владелец токена |
| `committed` | Статья и подтверждение сохранены в staging | Общая проверка и последующая публикация координатором |
| `needs_work_source` | Текст не найден после завершенных поисков на обоих дисках | `claim(mode:'work')` |
| `blocked_access` | Один из нужных источников недоступен | Восстановить доступ и переоткрыть задание |
| `needs_review` | Не подтверждена публикация, победитель, тип рейтинга или другой редакционный факт | Решение координатора |
| `excluded` | GEO-рейтинг в интересах GAEO/Алексея или другое явно исключенное семейство | Не выдавать в работу |

Для `needs_work_source` модуль требует **две** записи поиска со статусом `not_found` и `complete: true`. Во всех релевантных поисках должны быть просмотрены оставшиеся страницы: незавершенные `next_offset`, `nextOffset`, `nextPageToken`, `next_page_token`, `next_cursor`, флаги `partial`/`truncated` запрещают этот статус. Частичная выдача не доказывает отсутствие файла.

```javascript
const state = load('gaeo.rankings.state');
await queue.block({
  taskId: state.taskId, ownerId: state.ownerId, requestId: state.requestId,
  token: state.token,
  operationId: state.requestId + '-source-block',
  status: 'needs_work_source',
  reason: 'Полноценный текст не найден после проверки обеих папок и поиска по названию.',
  sourceChecks: [
    {provider: 'google-drive', status: 'not_found', complete: true, checkedAt: actualIsoTime,
      queries: ['фактически выполненные запросы'], locations: ['фактически проверенные папки/URL']},
    {provider: 'yandex-disk', status: 'not_found', complete: true, checkedAt: actualIsoTime,
      queries: ['фактически выполненные запросы'], locations: ['disk:/реальный/путь'],
      requestId: 'подтвержденный ID чтения API-моста'}
  ]
});
```

Это форма, а не готовые доказательства: подставляй только фактические результаты. При ошибке доступа укажи `blocked_access` и запись со статусом `inaccessible` или `error`. При редакционном конфликте — `needs_review` и конкретные противоречащие источники. После фиксации причины этот чат завершает свое 1 задание.

Если чат прекращает работу по иной причине, живой резерв можно вернуть через `release` с постоянным `operationId` и объяснением. Повтор старого `release` не снимает резерв нового владельца. Вторую статью в этом чате не брать.

## 8. Сохранение статьи одним коммитом

Сначала полностью закончи RU, EN, версии ссылок и список изображений. `submit` не принимает промежуточные фрагменты. Проверки модуля выполняются до изменения ветки и повторяются после каждой гонки.

Разрешенные входные файлы:

- 1 JSON: `{path:'src/data/rankings/articles/<id>.json', content: полныйUTF8Текст}`;
- изображения: `{path:'public/assets/rankings/<id>/имя.jpg', sha:'подтвержденный GitHub blob SHA'}`.

Для изображений сначала создай blob из **реальных существующих байтов** через `github_create_blob`. Передавай байты программно; не выводи Base64 в чат и не набирай его вручную. Создание blob еще не меняет ни ветку, ни сайт. Если байты недоступны, не подставляй неработающую ссылку или заглушку.

Модуль создает JSON статьи, все ссылки на изображения, квитанцию и статус `committed` **одним tree/commit**. Для будущих исполнителей это единственный способ сохранения результата.

До создания blob модуль читает манифест из того же SHA, что и актуальное задание, и проверяет обязательные версии RU/EN/CN, отсутствие pending URL и точность выбранных клиентских ссылок. После каждой гонки ветки он заново читает манифест из новой вершины перед сохранением. Квитанция фиксирует путь, SHA файла манифеста и коммит его чтения. Поэтому проверка ссылок работает и в обычном чате без локальной сборки сайта.

```javascript
const state = load('gaeo.rankings.state');
const submissionFiles = [
  {path: `src/data/rankings/articles/${state.taskId}.json`,
    content: JSON.stringify(finishedBilingualArticle, null, 2) + '\n'},
  ...confirmedImageBlobs // элементы {path, sha}; [] при отсутствии изображений
];
store('gaeo.rankings.submissionFiles', submissionFiles);
const result = await queue.submit({
  taskId: state.taskId, ownerId: state.ownerId, requestId: state.requestId,
  token: state.token, submissionId: state.submissionId, files: submissionFiles
});
store('gaeo.rankings.result', result);
text(result);
```

`submit` отвергает чужие пути, перезапись уже существующей статьи, изображения без упоминания в JSON, новый победитель, неполный перевод, небезопасные URL, пропущенные опубликованные версии, ссылки на pending-публикации, измененные клиентские URL и повтор уже принятого `submissionId` с другим содержимым. Он всегда передает `expected_sha` и `force:false`, а новый коммит имеет 1 родителя — прочитанную текущую вершину. При параллельном изменении берет свежую очередь и переносит только собственную статью на новое основание.

Ошибки `MISSING_PUBLISHED_VERSION`, `UNREGISTERED_CLIENT_URL` и `PENDING_PUBLICATION` означают, что статья еще не принята: исправь указанный адрес или список в том же задании. Если корректный адрес или статус установить невозможно, запиши конкретный `needs_review`. Для уже принятого результата повторный `submit` сверяет исходную квитанцию и байты файлов; последующее обновление реестра не превращает сохраненный коммит в неопределенный результат.

После записи модуль перечитывает очередь, квитанцию и SHA всех файлов из фактической ветки. Ссылку на коммит возвращает только после этого. При повторе он находит первоначальный принятый коммит по квитанции. Служебные непринятые Git-объекты, созданные при гонке, не считаются результатом.

Ни `workflow_dispatch`, ни merge в `astro-source`, ни запись в `main` в этот процесс не входят. Пометка `[skip ci]` дополняет изоляцию ветки, но не заменяет ее.

## 9. Что сообщить в конце

Дай название статьи и категорию, фактический статус, подтвержденную ссылку на коммит в `rankings-staging`, количество языковых версий, внешних версий и изображений. Укажи, что коммит ожидает общей публикации. При отсутствии текста перечисли проверенные хранилища и статус второго прохода. При неопределенном результате сохрани и сообщи идентификаторы восстановления; успех без подтверждения не объявляй.

## 10. Только для координатора: последующая публикация

Публикацию выполняет отдельная задача после накопления готовых статей. Обычные исполнители этот раздел не выполняют.

1. Приостановить новые резервы (`queue.paused: true`) отдельным изменением через CAS. Дождаться завершения или явного освобождения активных резервов; не отбирать их принудительно.
2. Зафиксировать проверяемый SHA `rankings-staging`. Сверить квитанции, список готовых статей, отсутствие дубликатов и исключенных семейств. Задания без текста остаются в очереди, публичные страницы для них не создаются.
3. Получить актуальные `astro-source` и `main`. В отдельной рабочей ветке объединить готовую очередь с текущим `astro-source`, сохранив все параллельные правки сайта. Не делать force-push и не подменять основную ветку старым полным деревом staging.
4. Выполнить проверки контента/ссылок, сборку, существующие обязательные проверки проекта, а также визуальную проверку новых страниц и категорий на компьютере и телефоне. Если нет локального CLI, эту часть передать задаче с рабочей средой; резервирование и обычная подготовка статей от CLI не зависят.
5. По отдельному поручению публикации перенести проверенный результат в `astro-source`. Это запустит штатный выпуск сайта. Дождаться его завершения и проверить публичные RU/EN URL, картинки, FAQ, canonical/hreflang и sitemap.
6. Зафиксировать фактическую публикацию отдельно от `committed`, затем синхронизировать основу `rankings-staging` безопасным обычным merge и возобновить новые резервы. Не менять ID уже обработанных семейств или квитанции принятых статей.

## 11. Проверка реализации очереди

```bash
node scripts/qa_rankings_queue.mjs
```

Проверка использует локальную модель неизменяемых Git-объектов и реальной семантики fast-forward/CAS. Она проверяет конкурирующие резервы, конкурентные и повторные результаты, утрату ответа после записи, восстановление по квитанции, истечение срока, продление, чужие пути, существующие файлы, изображения, поиск на двух дисках и второй проход Work. Отдельно проверены обязательные RU/EN/CN версии, точность клиентских URL, pending-публикации и изменение манифеста во время гонки. Тест не обращается к GitHub и не публикует сайт.

## 12. Переход на текущие названия GitHub-инструментов и режим подборок

Модуль сам обращается к абстрактному адаптеру с именами `mcp__codex_apps__github_...`. В некоторых новых чатах реальные инструменты называются `mcp__GitHub__fetch`, `mcp__GitHub__fetch_file` и т. д. При такой схеме передавай адаптер, который переводит имена и нормализует ответ (один из вариантов, без создания новых подключений):

```javascript
const legacyPrefix = 'mcp__codex_apps__github_';
const call = async (name,args) => {
  const shortName = name.startsWith(legacyPrefix) ? name.slice(legacyPrefix.length) : null;
  const tool = tools[name] || (shortName && tools['mcp__GitHub__' + shortName]);
  if(!tool) throw new Error('Missing connected GitHub action: ' + name);
  const result = await tool(args);
  return result?.result && !result?.structuredContent ? {structuredContent:result.result} : result;
};
const {createRankingsQueue}=Function(moduleSource.replace(/^export /gm,'')+'\nreturn {createRankingsQueue};')();
const queue=createRankingsQueue({call});
```

`moduleSource` — содержимое **`scripts/rankings-queue.mjs` из зафиксированного SHA**. В среде без `store/load` создавай и выводи идентификаторы в отдельном вызове до первого `claim`, затем повторно передавай их литералами в следующих вызовах. Не считай локальную переменную другой изолированной среды сохраненной. Для послеошибочного восстановления используй исходные ID из результата предыдущего вызова и `recover`, а не новые ID.

**Режим товарной подборки**: если задача имеет `contentType:'selection'`, `firstPlace:null` и `firstPlaceStatus:'not-applicable-selection'`, это законная запись `ready` после активации координатором. Заполняй `article.contentType:'selection'`, `article.entityType:'Product'`, все 11 позиций с точными `entry.url`, все 11 неповторяющихся партнерских ссылок в `clientLinks`, `source.firstPlaceVerification.status:'not-applicable-selection'` с указанием исходника и секции и реальной даты. Не присваивай победителя, баллы или фиктивные отзывы. Остальные правила RU/EN, отсутствия новых иллюстраций и одного коммита остаются прежними.

Если текущая очередь еще помечает `INDEX-P001` как `needs_review` с указанием на старые резервы, **не обходи этот статус**: координатор переведет в `ready`, когда старые исполнители завершат свои резервы и новая версия модуля станет безопасной для всех участников.
